# C11 完整支持与工程验收

用户要求的终点是完整 C11 特性支持，并进一步用 GCC 源码构建证明 Naru
的工程能力。当前目标保持进行中，现有真实项目用例通过不代表完成。

检查基准是 [WG14 N1570](https://www.open-std.org/jtc1/sc22/wg14/www/docs/n1570.pdf)。
后续还需要逐项登记适用的缺陷报告及解释，区分标准约束、实现定义选择、
未定义行为和宿主扩展。当前目标平台是 Windows x86_64 LLP64。

## 验收顺序

1. 补齐标准语言规则和必需诊断：翻译阶段、作用域、类型兼容、声明、
   表达式、对象存储期、初始化、控制流和链接。
2. 完成 C11 新特性和条件特性：泛型选择、静态断言、对齐、原子、VLA、
   复数及线程相关能力。标准允许条件支持不等于本项目把缺失项算作完成；
   能力声明、目标实现和测试必须一致。
3. 验证全部系统标准头文件及库接口的组合、宏与 ABI。继续链接实际系统
   C 库，不通过手写替代头文件掩盖兼容问题；缺失的宿主库接口单独登记。
4. 扩大未经改写的真实项目输入：预处理密集项目、大翻译单元、多翻译单元、
   聚合 ABI、并发和复杂构建图。记录正确性、编译时间、内存和运行结果。
5. 接入具体版本的 GCC 构建，补齐它要求的 GNU 方言、C++ 和构建工具接口。
   固定源码版本、依赖版本、配置参数、构建阶段与产物测试，才算完成验收。

[GCC 官方构建前提](https://gcc.gnu.org/install/prerequisites.html) 当前要求
ISO C++14 编译器；GCC 4.8 之前才以 C89 编译器为自举前提。因此现代 GCC
构建不能仅靠完成 C11 宣称通过。历史版本的 C 阶段和现代 GCC 阶段分别记录。

## 可追踪的覆盖清单

`tests/c11/conformance.json` 登记标准条款、功能组、现有证据和剩余工作。
`partial` 只表示已有部分实现，`missing` 表示尚缺能力；引用某个测试文件
不代表对应条款的所有段落都验证完毕。清单没有给出虚构的标准覆盖百分比。

`tests/c11_conformance.py` 运行其中的逐条验收输入，合法程序与独立 Clang
结果对照；需要诊断的程序检查错误和旧产物保护。定义为未定义行为的个别
输入不把 Clang 必须拒绝作为标准要求，其策略在夹具中明确标记。

Naru 编译在 PATH 为空且禁止子进程的 Job 内串行运行，512 MiB、30 秒上限。
成功产物检查进程内后端报告并执行；报告保存编译器、后端、规则和清单哈希。
运行中的输入变化会使整个验收失败。尚无夹具的功能组会列入报告，不能被
“全体配置用例通过”掩盖。报告始终保留 `full_c11_conformance_claimed=false`，
直至完整验收依据建立。

```powershell
python tests/c11_conformance.py --feature constants
python tests/c11_conformance.py
python tests/exact_float.py
```

## 当前常量表达式工作

常量运算策略在 `dialects/c11/constants.stx`。通用 `float.*` 原语通过 APFloat
保持 MLIR 浮点格式精度，C11 规则选择转换、舍入、范围及错误策略。
整数常量表达式与静态算术初始化分别判断；枚举、数组界限、指定下标、
case、对齐和静态断言使用统一的整数常量关系。

`_Generic` 的所有关联继续经过语义检查，仅选中的源表达式参与常量求值；
控制表达式不产生运行时效果。`sizeof` 对操作数检查对象类型并剪枝，避免
常量改写进入本来不求值的子表达式。仍需继续覆盖全部地址常量、类型约束、
复杂作用域及目标浮点环境，不把这一轮视为整个 6.6 条款完成。

静态聚合初始化保留 `SourceConstant(value, isICE)`，直到数组元素或成员的
目标类型确定。算术初始化可以接受折叠后的整数，指针初始化仍要求原表达式
符合整数常量表达式规则，不能仅凭最终数值为零判断。该事实跨嵌套花括号、
数组/结构体指定初始化及联合体成员转换保留。系统 `offsetof` 在当前语义
环境中完成类型，再作为整数常量参与枚举、下标和静态断言。

## 联合体对象表示

联合体的语言成员与 LLVM 存储表示分离。当前 LLP64 适配以 1、2、4、8
字节整数单元保存完整对象，并保留布局要求的大小和自然对齐。包含指针
的联合体具有 8 字节对齐，因此每个自然对齐的指针位置都有完整的重定位
槽位，不再因为另一成员先被选为浮点/数组/结构体而切分符号地址。

`c11.union_storage` 通过共享 `storage` 规则转换对象位模式，不做算术
转换。标量、数组、结构体、嵌套联合体及非首成员初始化使用同一条路径，
局部源表达式只降低一次。`storage` 仅接收目标提供的标量位宽和偏移，
不认识 C 类型；有序源片段与目标窗口通过单向游标匹配，避免构造与整个
聚合对象一样宽的中间整数。当前 C 适配选择小端布局。

2026-10-12 的额外探测复现了复杂符号转换导致的 LLVM 销毁断言；原防护
误用环境对象身份比较，无法触发。该防护已移除，普通对象地址、函数地址、
多地址数组/结构体和嵌套联合体改由完整槽位保留。共享后端另用 LLVM
翻译接口检查实际结果，对不能生成常量的操作给出诊断，并在失败前释放
未挂到基本块的指令依赖，避免清理时崩溃。后端不识别任何 C 关键字。

新增 10 个合法 C11 输入，每个对照 Clang 并运行 O0/O2；整个逐条语料现在
为 81 个输入、162 项检查。这仍不代表完整初始化支持：全部地址常量形式、
额外对齐组合、省略花括号、链式指定、覆盖初始化等继续留在覆盖清单中。
